# V1: two live graphical sessions under SDDM — FAIL on stock Omarchy 4.0.2

Tested 2026-09-02 in the QEMU VM (kid-ada live on tty1, kid-vm as the second user) and, for the
one non-destructive call, on omarky-air itself. Driver notes in `scripts/v1-two-sessions.sh`.

## What happens

| Step | VM | Real laptop |
| --- | --- | --- |
| `Seat.SwitchToUser(user, session)` over D-Bus | returns success, does nothing | not tried |
| `Seat.SwitchToGreeter()` over D-Bus | SDDM starts a second greeter; its helper exits with 5, `SDDM::Auth::HELPER_TTY_ERROR`, "Jumping to VT 1", display removed | identical |
| Sessions afterwards | one graphical session, unchanged | one, unchanged |

So on Omarchy 4.0.2, with SDDM in its Wayland-greeter mode (`DisplayServer=wayland`, the
greeter is itself a Hyprland compositor started by `CompositorCommand`), **SDDM cannot open a
second display while a session holds the seat**. Fast user switching through SDDM does not
exist here. This is SDDM's known limitation in Wayland mode, not something our theme can fix.

Two smaller facts from the same run:

- Omarchy's greeter is password-only and logs in `userModel.lastUser`; the account is chosen by
  editing `/var/lib/sddm/state.conf`, not by the person at the keyboard. Our portal (R-LOGIN)
  replaces that, but it will still be one greeter at a time.
- The kid's Ctrl+Alt+F-key exposure question is moot until a second session can exist.

## What this means for the design (decision needed from Mark)

R-EXIT-3 assumed Pause = lock the kid's session and `SwitchToGreeter` for the parent. That
mechanism is unavailable. The options:

1. **Pause without SDDM.** A root helper (polkit-gated, parent password) starts the parent's own
   session on a free VT by opening a PAM session directly (a dedicated PAM service with
   `pam_systemd`, then `Hyprland` as the parent on that VT), while the kid's compositor stays alive
   on its VT. logind then handles Ctrl+Alt+F-key switching between the two, and the parent's session
   locks on switch-away as the spec already requires. This is what SDDM would do minus the greeter.
   Feasible, moderate work, needs its own V-check.
2. **Pause = lock and log out** for v1 (the kid's apps close), keep the two-button modal, and
   revisit fast switch when the mechanism in option 1 exists.
3. Wait for upstream multi-user (Omarchy 4.1 was rumored to add it) and see what login manager
   arrangement it brings.

Recommendation: ship the modal with both buttons, implement Finish now, and build option 1 as its
own ticket with a Phase 1 check before promising Pause in the UI (I-6: never show a control that
is not enforced).

## Side effect on the laptop, and the fix

The failed greeter attempt was not harmless on real hardware: it left the parent's session marked
inactive in logind, and Hyprland's input devices (keyboard, trackpad) were revoked and not
re-acquired, so the desktop would have ignored the keyboard. Recovery: `chvt 2; chvt 1`, then
`loginctl activate <session>`, then `udevadm trigger --subsystem-match=input --action=add`, after
which Hyprland listed the Apple keyboard and trackpad again. Whatever mechanism Pause ends up
using must never call `SwitchToGreeter` on this stack.
