# V4: per-kid LUKS key slots — PASS

Machine: the test VM on omarky-air (`docs/vm.md`), Omarchy 4.0.2 unattended install, encrypted,
`/dev/vda2` LUKS2. Date: 2026-09-02. Script: `test/phase1/v4-luks-slots.sh` (run as root inside
the VM; it re-execs itself under sudo because sudo closes the process-substitution key files).

## Slot mechanics, inside the VM

| Step | Result |
| --- | --- |
| Add three kid passwords as slots, authorized by the owner's passphrase only | PASS, four slots |
| Change one kid's password: add the new one authorized by the old, remove the old | PASS, slot count unchanged |
| Remove a kid: their password no longer opens the disk | PASS |
| Owner's passphrase still opens the disk | PASS |

Final layout: slot 0 owner, slot 1 `kid-ada`, slot 4 `kid-ben` (changed password). LUKS2 reuses
freed slot numbers, so a slot number is stable only while the slot lives; the boot-slot mapping
(R-BOOT-3) must be rewritten by provisioning whenever a slot is added, changed, or removed.

## Boot with a kid's password

The VM was powered off and booted; `kidpass-ada` was typed at the disk prompt through QMP. The
disk opened and the system came up to a desktop, SSH reachable. **It autologged the owner**,
because stock Omarchy autologs the owner after any successful unlock. That is the exact hazard
R-BOOT exists to remove, and V7 tests the fix in the same VM.

## Consequences for the spec

- R-SEC-4 stands. `luksAddKey --key-file=<(owner) <newkey>` needs no interactive input, so the
  wizard can add slots with the parent's password it already holds for the session.
- Provisioning must maintain `/etc/omarchy-kids/luks-slots` on every slot change (new item under
  #10) because slot numbers are reused.
- Changing a kid's password is two LUKS operations (add new, remove old), both authorized by the
  old password; if the old one is lost, the parent's passphrase authorizes the add and the removal
  targets the old slot by number.
