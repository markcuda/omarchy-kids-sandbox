# V5: the parent-password verifier behind PAM — PASS

Machine: omarky-air (Omarchy 4.0.2, libxcrypt with `libcrypt.so.2`). Date: 2026-09-02.
Code: `bin/omarchy-kids-authd`, `bin/omarchy-kids-parent-auth` (#35). Scripts:
`test/phase1/v5-verifier.sh` with `test/phase1/pam-try.py` (a libpam client over ctypes, so no
extra packages are needed to drive a PAM stack).

## What was tested

Test accounts only. `kid-test` played the parent (the verifier was started with
`--parent kid-test`); `kid-ada` played the kid. A scratch PAM service tried the kid's own
password first through `pam_unix`, then the parent password through `pam_exec … expose_authtok
/usr/bin/omarchy-kids-parent-auth`, then denied.

| Case | Result |
| --- | --- |
| Kid's own password, stack run as the kid | success (pam_unix) |
| Parent password, stack run as the kid (lock-screen case) | success (verifier) |
| Parent password, stack run as root (SDDM case) | success (verifier) |
| Wrong password, three times | denied |
| Parent password right after three misses | denied: 30 s rate limit |
| Kid's own password during the limit | success: the kid path is untouched |
| Candidates in the daemon's journal | none |

## Why this matters

The installer path's lock-screen helper runs `sudo -k -S` inside `pam_exec`, and its reviewer
found that copying it onto SDDM's root-run stack would accept any password without `seteuid`.
Here the PAM helper only forwards the candidate to a root daemon that compares it against the
parent's shadow hash, so the result is identical whoever runs the stack, and no `seteuid` is
needed. The rate limit is the daemon's own and never touches the parent's login `faillock`.

## Notes

- Arch's libxcrypt ships `libcrypt.so.2`; the daemon tries `.so.2`, then `.so.1`, then `.so`.
- The socket is world-connectable by design: kids' sessions must be able to ask. The daemon's
  rate limit is the defense against a local oracle attack; the exit modal adds its own.
- Unit hardening (`ProtectSystem=strict`, `ProtectHome`, `RestrictAddressFamilies=AF_UNIX`) ran
  fine under socket activation.
