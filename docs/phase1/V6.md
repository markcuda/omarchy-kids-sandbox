# V6: the hub's five unknowns on Omarchy 4.0.2

Machine: omarky-air (2019 MacBook Air, T2), Omarchy 4.0.2, kernel 7.1.8-t2, encrypted install.
Started 2026-09-02. Script: `test/phase1/v6-tmpfs-exec.sh`.

## Which tmpfs mounts allow exec — DONE

| Mount | FS | Options | Exec |
| --- | --- | --- | --- |
| `/tmp` | tmpfs | `rw,nosuid,nodev,…,usrquota` | **allowed** |
| `/dev/shm` | tmpfs | `rw,nosuid,nodev,…` | **allowed** |
| `/run/user/1000` | tmpfs | `rw,nosuid,nodev,mode=700,uid=1000` | **allowed** |
| `/var/tmp` | btrfs (`@` subvolume) | `rw,…` | **allowed** |

**Finding.** A `noexec` home (spec R-FND-2) does not stop a kid from running a downloaded
binary: every writable temp location on the box allows exec. `nosuid` and `nodev` are set
everywhere, so privilege escalation through those paths is not the risk; running arbitrary
unprivileged code is.

**Consequence for the spec.** Machine-wide `noexec` on `/tmp` is off the table (I-1: it would
break the parent's own builds). The per-kid answer is a private, `noexec` `/tmp` and `/dev/shm`
for kid sessions, delivered by `pam_namespace` (polyinstantiated tmpfs with `mntopts=noexec`) on
both the SDDM stack and the `systemd-user` stack, because Omarchy launches apps through the
user's systemd manager, which does not inherit the login session's mount namespace. `/run/user/<uid>`
can be handled the same way or left as a stated fence. Tracked as a new item under issue #10
(provision) and added to the R-DESK-2 login checks.
